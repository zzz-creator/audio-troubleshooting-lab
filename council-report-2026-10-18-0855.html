LLM Council — Report

What can we improve in the Audio Troubleshooting Lab?

Convened 18 October 2026 · 10 advisors (core five + 5-seat panel) · 10 anonymous peer reviewers · 1 chairman
The framed question What should we improve in the project — codebase maintainability, funnel/conversion design, product/pedagogy priorities, and process risks? What is the highest-leverage improvement, what is decaying, what is over-engineered or missing? Context: single-page React+Babel-via-CDN app, no build step, GitHub Pages, embedded in Circle iframes; free tier feeds a paid membership; staging v242 vs. production v108 with hand promotion; soft paywall; a recent signed-cookie unlock commit; a single maintainer.
Where the council agrees
  • The manual promotion ritual is the #1 problem — 10/10. Production sits ~134 versions and ~1,000 lines behind staging; two 13,650-line HTML shells maintained by hand; the cache-buster is bumped in multiple places per push. One forgotten &v=N ships stale content silently; one wrong-direction copy reverts shipped fixes.
  • The HMAC signed split-cookies + session-seal unlock is security theater — 10/10. The pepper ships in the bundle, Circle's access group is the real lock, and the stack creates an asymmetric failure: a bug there locks out a paying member.
  • The funnel is unmeasured. Conversion is the stated goal, yet nothing records drop-off between the email gate and the join panel. "Conversion work with no instrumentation is astrology."
  • Show Day's forks are dead weight; member onboarding comes first. The new-member path protects month-one churn (the fragile revenue); decide Show Day's free/paid split before building it at all.
  • Cheap, agreed hygiene: vendor @babel/standalone so the regression gate actually runs, handle the untracked .log, and reconcile or delete the two planning docs the funnel has overtaken.
Where the council clashes
  • Patch the fork vs. kill the fork. Majority (Executor, Pragmatist, Risk Assessor, Economist, Strategist, Contrarian): write scripts/promote.js — 15 minutes, zero deploy risk. Minority (Innovator, Outsider, First Principles): staging should be a branch, not a file — one artifact, dev flag, git-SHA cache-buster. Reviews split on direction (favoring the structural fix) but agreed on sequencing (script first). These are target state and first step, not true opposites.
  • Revert the HMAC vs. freeze it. Most said delete it; the Executor said freeze and never extend it. Peer review sided with caution — nobody wrote a migration path, and the crypto may exist because plain localStorage silently fails under Safari ITP inside iframes.
  • Ship now vs. measure first. The Expansionist said ship the funnel plan this week; Risk Assessor, First Principles, and Innovator said instrument first. Reviews near-unanimously flagged the Expansionist as the blind spot — shipping through the broken pipeline widens the drift. Defensible middle: only the pre-approved 2026-07-10 email-gate move.
Blind spots the council caught
  • The iframe storage trap. Everyone said "revert to a plain localStorage flag" — nobody checked whether it already fails silently under Safari ITP / Chrome's third-party cookie phase-out inside Circle embeds. It may be why the HMAC was built. The paywall may be broken in production with no error surface.
  • No migration plan. Reverting the HMAC and jumping production v108 → v242 both strand existing members' stored state.
  • Runtime cost is a conversion problem. 956KB of HTML plus in-browser Babel compilation on every load, inside mobile iframes — slow first paint on the phones where Circle embeds actually open. Five reviews flagged it independently.
  • The evidence doesn't hold. Line counts and version numbers differ across advisors; only one central claim is falsifiable — the Executor's "content.js is a strict subset" — and it must be verified with a real diff before acting on it.
  • No user voice. Zero interviews or drop-off surveys; accessibility of an audio tool; GDPR/consent exposure with Kit email capture.
  • Bus factor. No backup or export of the content graph — the actual product — and no release runbook.
  • Two unused assets: the ~850-byte HTML diff is the environment switch (not trivially deletable), and the COPY LIBRARY ENTRY share-builder is a distribution engine hiding in a training tool — six reviews endorsed it as the strongest unique idea.
The recommendation

The binding constraint is one maintainer's release energy. Everything else is downstream of releases that can't break a funnel you can see. In order:

  1. Automate promotion (this week). One promote.js: diff staging→production and refuse regressions, copy the content file, bump every &v=N from a single version constant, run all three checks, print the embed URLs. Verify the subset claim with a real diff first. Vendor @babel/standalone. Gitignore the log.
  2. Instrument before rewriting. One event per funnel stage (a Kit tag or a sendBeacon ping is enough). Name the drop-off number you're currently guessing at.
  3. Freeze the HMAC; don't revert yet. Verify unlock behavior in a real Circle iframe on Safari and Chrome, write a one-page migration note, then reduce it to a plain flag.
  4. Then ship the cheap funnel win — the already-approved move of the email ask from the Start Here finale to after the first win inside Run the Show — now that you can measure it.
  5. Build the new-member path, not Show Day. Decide Show Day's split or delete the doc. Treat staging-as-branch / single artifact / SHA cache-buster as the target state to adopt after promote.js proves the workflow. Take the share-builder seriously once the funnel is visible. Back up the content graph; test first paint on a phone.
The one thing to do first
Run one real diff of content-staging.js vs content.js to confirm the strict-subset claim, then write scripts/promote.js — a single command that runs the three checks, refuses staging→production regressions, copies the file, bumps every &v=N from one version constant, and prints the embed URLs to re-paste in Circle.

Fifteen minutes to an hour. It is the one fix all ten advisors ranked first, it removes the largest silent-failure risk in the repo, and it is the precondition for every other change on this list.

Advisor responses

The Contrarian Core five

The HMAC unlock system is security theater, and it's your most expensive line of code. The pepper is extractable from the bundle — your own README admits it. Cold visitors already receive all 13,650 lines of engine HTML; the split cookies, install ID, and session seal protect nothing Circle doesn't already protect, while adding a crypto module, cookie-migration paths, and a test matrix a solo maintainer must maintain forever. Delete it or reduce it to one flag. Complexity you can't afford is worse than a paywall someone can bypass.

The real decay is the manual promotion between two drifting files. Staging v242 vs. production v108 — a 1,019-line content divergence maintained by hand, with a cache-buster bumped in multiple places per push. One forgotten &v=N, and members load stale content. Highest-leverage fix: one promote.js that copies staging→production and rewrites every version literal atomically.

Show Day has been an unbuilt decision for four months. Your own review flagged Fork A (member onboarding first) as protecting month-one churn — the fragile revenue — yet the forks never got decided. Building Show Day now optimizes the long-tenure member while your newest paying member lands in randomness.

Missing: funnel instrumentation. You cite conversion as the business goal but measure nothing between email gate and join.

The First Principles Thinker Core five

You're asking which of four areas to improve. Wrong question. The real problem: a one-person project is paying a compounding tax on every commit, and no feature in any of those four buckets matters while it does.

The 956KB shell is identical between staging and production except one <script src> line — yet it's maintained twice, by hand. That is the decaying asset: not the code, the promotion ritual. Everything else follows from it — the content drift, the stale-shell risk, the version-pairing commits cluttering your log.

The signed split cookies + session seal are the tell. You built real cryptographic complexity to defend a paywall your own README admits isn't the real protection, while leaving genuinely unprotected the failure that ships silently: a hand-copied divergence or stale cached shell. Fix the leak you have, not the one you invented.

Highest leverage: one command that copies content-staging.js → content.js, bumps N everywhere, runs the three checks. Then: "pass/fail vs. no-scoring" isn't an unresolved fork — it's two incompatible pedagogies never reconciled. Decide what the tool teaches before building Show Day. Conversion work with no stated drop-off measurement is astrology.

The Expansionist Core five

The undervalued asset is your own content graph. Every guided chain in content-staging.js — patch, power, gain, ring-out — is structured, machine-readable pedagogy nobody else has. Export it and each lesson becomes a YouTube walkthrough script, a Circle post, a printable System Check card, and the daily Show Day feed. One content source, five distribution surfaces.

Highest leverage: ship the 2026-07-10 funnel plan. It's written, panel-approved, and mostly a policy re-slice of existing code. Staging is at v242, production at v108 — you're 134 experiments ahead of your revenue. The conversion lift is sitting unbuilt while you polish the simulator.

Show Day is the retention engine everyone's underrating. Resolve the forks by shipping the loosest version this week.

Decaying: the staging/production split — 134 versions of manual copy-promotion is a time bomb; one promote.js costs an hour. Over-engineered: signed split cookies + session seal securing a soft paywall whose real lock is Circle.

The Outsider Core five

Nobody outside this repo could ship a single change here. Two 956KB HTML files that differ by ~850 bytes, promoted by hand, a cache-buster bumped "in multiple places" — that's not a workflow, it's a ritual only you know. The content files have diverged by ~1,000 lines, which means your staging sandbox is teaching lessons production doesn't have, or vice versa. Nothing checks it.

Highest leverage: one file pair, not two. Make index.html the only engine, switch environments with a single ?env=staging flag or a tiny build script. That deletes the manual copy, the drift, and most of the cache-buster problem in one move.

Over-engineered: the signed-cookie unlock system — security theater; the pepper ships to every browser, and you've said the real gate is Circle.

Missing: an outsider cannot tell what a new visitor does in the first 60 seconds, or why they'd pay. Ship one clear hero scenario and instrument it — you're optimizing gates on a path whose first step is unmeasured. Decaying: the written plan, already overtaken by the funnel.

The Pragmatist Panel · Practical Advisor

The two ~13,650-line HTML files differ by ~20 lines — one file maintained twice, by one person, via manual copy. content.js has been frozen at v102 since July 24 while content-staging.js ran to v242: 1,019 lines of production content are a stale mirror. Every engine fix now requires a double-edit you will eventually forget.

The realistic fix is not "adopt a build step" — it's one 30-line Node concat script: template.html + content.js → index.html, version injected from git describe. It kills three wounds: the manual copy, the &v=N bump scattered across Circle embeds, and the visibly failing promotion step.

Over-engineered: the signed split cookies + session seal — maintenance burden buying false confidence. Missing: measurement — one funnel event log, even a Kit tag per stage. Decaying: the Show Day forks, open three months — that's not unresolved, that's dead. Ship a default: new-member path first, no scoring, free.
